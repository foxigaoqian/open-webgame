# Editorial Authority System

# 1. Purpose

A strong game wiki should behave like a maintained editorial product, not a pile of SEO articles.

Every important page should tell the reader:

- what kind of page this is;
- when it was published;
- when it was actually updated;
- which game/build/status it was checked against;
- which claims are official versus inferred/player-reported;
- which sources support the important facts.

# 2. Page classes

Use explicit page classes:

- Entity homepage
- Maintained guide
- Status tracker
- Dated report
- FAQ hub
- Source ledger
- Reference page
- Utility/tool page
- Playable page

Do not let every page collapse into the same generic article template.

# 3. Maintained guide metadata

Recommended visible metadata:

- category / page class;
- H1;
- short deck;
- editorial desk/byline;
- published date;
- updated date;
- reading time;
- checked build/status where relevant;
- reporting rule;
- sources.

Never invent a fake person.

Use an honest label such as:

> <Site Name> Editorial Desk

unless a real named author is responsible.

# 4. Reporting rule

A visible reporting rule should be short and consistent.

Example:

> Official store fields, developer announcements and developer-tagged statements can confirm a claim. Player posts can identify problems and workarounds, but do not by themselves prove a universal mechanic or fix.

Adapt to the project.

# 5. Source hierarchy

Preferred:

1. official game/store page
2. official developer/publisher announcement
3. official patch notes/devlog
4. developer-tagged community reply
5. directly verified gameplay
6. named press/interview
7. multiple community reports
8. single community report
9. third-party guide as a research lead only

The source hierarchy should influence the visible claim status.

# 6. Revision discipline

Do not update the visible "updated" date unless material page content actually changed.

For important pages, keep a small internal revision record:

- date;
- game/build state;
- what changed;
- source.

# 7. Dated reports

Dated reports preserve history.

They should answer:

- what happened?
- when?
- who announced it?
- what is confirmed?
- what remains open?
- which evergreen pages need updating?

Do not silently rewrite a dated historical report to sound as if later knowledge existed at publication time. Add a clearly dated update note instead.

# 8. Trackers

Trackers preserve one stable URL.

Good tracker fields:

- current status;
- last checked;
- latest build;
- confirmed;
- fixed;
- player report;
- unknown;
- timeline;
- sources.

# 9. Public corrections

When a material fact was wrong:

- correct the page;
- update the source ledger;
- leave a concise correction note when useful.

Trust is strengthened by visible correction behavior, not by pretending the mistake never existed.
